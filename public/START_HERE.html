### 1.2 System Boundary & Lifecycle Scopes
- **Phase 1 (Current Baseline)**: Architecture, formal domain modeling, API contracts, security threat modeling, and test planning.

## 3. Index Justification & Redundancy Review

### 3.1 Removal of Redundant Primary Key Indexes
In the initial draft, explicit DDL statements included:
- `CREATE INDEX ix_users_id ON users (id);` (REDUNDANT)
- `CREATE INDEX ix_tasks_id ON tasks (id);` (REDUNDANT)

**Correction**: Both statements are removed. In PostgreSQL and SQLite, declaring `PRIMARY KEY (id)` automatically creates a unique B-Tree index on `id`. Adding a secondary non-unique index on the exact same column:
1. Wastes disk space and shared buffer pool memory.
2. Increases write amplification and write latency on every `INSERT` and `DELETE`.
3. Creates index bloat without offering any query optimization benefit.

### 3.2 Query-to-Index Justification Matrix

| Index Name | Index Columns | Expected Query Pattern in Application | Justification & Expected Query Plan |
| :--- | :--- | :--- | :--- |
| `ix_users_email` | `(email)` UNIQUE | `SELECT * FROM users WHERE email = :email` | Fast single-row index lookup for `POST /api/v1/auth/login`. Enforces database-level uniqueness across registrations. |
| `ix_tasks_user_id` | `(user_id)` | `DELETE FROM users WHERE id = :id` (Cascading) | Prevents sequential scans on the child `tasks` table when deleting user records. Essential for PostgreSQL foreign key locking performance. |
| `ix_tasks_user_id_status` | `(user_id, status)` | `SELECT * FROM tasks WHERE user_id = :uid AND status = :st` | Enables index-only or index bitmap scans restricted to the user's partition, filtering immediately on the lifecycle state. |
| `ix_tasks_user_id_created_at` | `(user_id, created_at DESC)` | `SELECT * FROM tasks WHERE user_id = :uid ORDER BY created_at DESC LIMIT :limit OFFSET :offset` | Satisfies both the tenant boundary filter and the ordering clause directly from the index, avoiding an in-memory `Sort` node. |
| `ix_tasks_user_id_title` | `(user_id, title)` | `SELECT * FROM tasks WHERE user_id = :uid AND title LIKE :prefix` | Optimizes tenant-scoped title searches. Replaces an unscoped single-column `title` index to preserve tenant partition locality. |

## 4. UUID Generation Strategy & Migration Behavior

### 4.1 Dual-Tier UUID Generation
UUID generation is implemented with a clear separation between the application tier and the database engine tier:

1. **Application Tier Generation (Client-Side Default)**:
   - Defined in SQLAlchemy 2.x declarative models via `mapped_column(UUID(as_uuid=True), default=uuid.uuid4)`.
   - **Benefit**: UUIDs are generated in application memory *before* emitting the SQL `INSERT`. This allows the application to construct complex parent-child relationship graphs, correlation IDs, and audit logs without waiting for a database roundtrip.
2. **Database Tier Server Default (`gen_random_uuid()`)**:
   - Defined in PostgreSQL DDL via `server_default=sa.text('gen_random_uuid()')`.
   - **Benefit**: Direct SQL executions (Alembic data seeding, batch ingestion scripts, or administrative repairs) automatically receive cryptographically secure UUIDv4 identifiers without application intervention.
   - **PostgreSQL Version Note**: `gen_random_uuid()` is built into core PostgreSQL (version 13+) and does not require enabling external extensions such as `uuid-ossp` or `pgcrypto`.

# ADR-001: Modular Monolith Architecture Pattern

**Status**: Approved  
**Date**: 2026-10-31  
**Authors**: Senior Backend Architect (Rayhan AI Architecture)  
**Stakeholders**: Engineering Team, System Architects

---

## 1. Context & Problem Statement

TaskFlow Orchestrator requires an architectural foundation that supports rapid feature delivery, strict ACID transactional boundaries, low operational complexity, and seamless multi-tenant isolation. 

The system must also support future evolutionary phases:
- **Phase 3**: Integration of asynchronous worker queues and background job dispatch.
- **Phase 4**: Autonomous AI planning agents executing through tool-calling interfaces (MCP).

A premature decomposition into microservices introduces distributed transaction hazards, network latency, deployment overhead, service-mesh complexity, and high cognitive load for small-to-medium engineering teams. Conversely, an unstructured "spaghetti" monolith degrades into tightly coupled code that cannot be scaled or modularized later.

---

## 2. Decision

We will structure TaskFlow Orchestrator as a **Modular Monolith** using **Python 3.11+ and FastAPI**.

The codebase will be strictly organized into domain-oriented packages with defined boundaries:
1. `app/auth`: Credential validation, token issuance, and cryptographic hashing.
2. `app/routers`: Explicit HTTP endpoint routing with input validation schemas.
3. `app/models`: Declarative persistence schemas and entity relationships.
4. `app/database`: Connection pooling, engine configuration, and transaction lifecycle.
5. `app/config`: Centralized, typed environment settings via Pydantic v2.

### Internal Communication Rules
- In-process module interactions must occur via typed interfaces or dependency injection.
- Direct raw cross-table mutations without going through domain constraints are prohibited.
- Shared persistence is mediated via standard SQLAlchemy 2.x sessions within a single transactional boundary per HTTP request.

---

## 3. Alternatives Considered

### Alternative A: Microservices from Day 1
- **Description**: Separate Auth Service, Task Service, and Notification Service into distinct network-accessible repositories and deployable containers.
- **Why Rejected**: Microservices require distributed transaction coordination (Saga pattern or 2PC), independent CI/CD pipelines, API gateway routing, and container orchestration (Kubernetes). At this stage, distributed microservices would drastically reduce engineering velocity without providing performance or organizational benefits.

### Alternative B: Traditional Layered (N-Tier) Monolith
- **Description**: Traditional horizontal layering (`controllers/`, `services/`, `models/`, `views/`).
- **Why Rejected**: Lacks vertical domain boundaries. Inevitably results in circular dependencies between services and prevents isolated testing or future extraction of specific bounded contexts (such as extracting the Task execution engine into a worker process in Phase 3).

### Alternative C: Serverless Functions (AWS Lambda / Cloud Functions)
- **Description**: Expose each route as an individual serverless function.
- **Why Rejected**: Introduces cold-start latency, connection pooling bottlenecks with relational databases (exhausting PostgreSQL connection limits without external proxy layers like AWS RDS Proxy), and complicated local test setups.

---

## 4. Consequences

### Positive Consequences
- **Unified Deployment**: A single deployable artifact (Docker container) that can be run on any cloud platform or container runner.
- **Transactional Integrity**: Atomic database transactions spanning user updates and task operations without distributed lock overhead.
- **High Developer Velocity**: Single codebase with instant local execution and rapid in-memory Pytest test runs.
- **Future-Proof Extraction**: Domain modules (e.g., Task execution engine) are already isolated behind clean interfaces, making future extraction into worker processes in Phase 3 straightforward.

### Negative Consequences & Mitigations
- **Shared Memory Space**: A memory leak or unhandled exception in one module could theoretically impact the entire process.
  - *Mitigation*: Comprehensive automated test suites, request timeouts, and process-level health checks.
- **Discipline Required**: Developers may be tempted to bypass domain boundaries.
  - *Mitigation*: Static code analysis, strict module import hierarchies, and peer code reviews.

# ADR-002: Backend Privileged Connection with Application-Level Authorization (No Supabase RLS)

**Status**: Approved  
**Date**: 2026-10-31  
**Authors**: Senior Backend Architect (Rayhan AI Architecture)  
**Stakeholders**: Security Engineering, Backend Architecture

---

## 1. Context & Problem Statement

TaskFlow Orchestrator is a multi-tenant platform where user data must be strictly isolated. A critical architectural choice is whether to enforce multi-tenant authorization at the **Database Row-Level Security (RLS)** layer (e.g., Supabase Postgres RLS policies) or at the **Application / Service Layer** via a backend privileged connection pool.

The system requires:
1. High-throughput connection pooling without session state thrashing.
2. Complete portability across any cloud-managed PostgreSQL provider (AWS RDS, GCP Cloud SQL, Azure, self-hosted Docker, Neon).
3. Fast, deterministic automated testing without requiring a live, external Postgres container with custom RLS extensions in every test run.
4. Prevention of tenant data leakage and ID enumeration attacks.

---

## 2. Decision

We approve and mandate **ADR-002: Backend Privileged Connection with Application-Level Authorization**.  
We explicitly **reject Supabase / Database-Level Row-Level Security (RLS)**.

### Architectural Rules:
1. **Privileged Backend Connection Pool**:
   - The application connects to PostgreSQL using a single privileged database user role (`taskflow_user`) managed by an SQLAlchemy 2.x connection pool (`pool_size=10, max_overflow=20, pool_pre_ping=True`).
2. **Mandatory Application-Level `user_id` Filtering**:
   - Every database query (SELECT, INSERT, UPDATE, DELETE) against user-owned resources MUST explicitly include `user_id == current_user.id`.
   - Creating tasks binds `user_id = current_user.id` automatically from the verified JWT identity context (`sub` claim).
3. **Anti-Enumeration 404 Status Code**:
   - Cross-user access attempts (e.g., User B attempting to read, update, or delete User A's task by UUID) MUST return **HTTP 404 Not Found** (rather than 403 Forbidden).
   - This prevents attackers from enumerating valid task UUIDs across tenants.
4. **Explicit Migration Ownership**:
   - All DDL operations execute via version-controlled **Alembic** migrations. Runtime `Base.metadata.create_all()` is strictly forbidden in production.

---

## 3. Detailed Comparison & Rationale

| Dimension | ADR-002: Application-Level Authorization | Supabase / Database-Level RLS |
| :--- | :--- | :--- |
| **Connection Pooling** | **Highly Efficient**: Connections are recycled across requests without transaction-level state manipulation. | **Poor Scalability**: Requires issuing `SET LOCAL role` or `SET request.jwt.claim` on every transaction, causing session variable pollution in connection pool proxies (PgBouncer). |
| **Cloud Portability** | **100% Portability**: Runs identically on any standard PostgreSQL instance without proprietary extensions. | **Vendor Lock-In**: Coupled to Supabase auth schemas, PostgreSQL procedural functions, and proprietary JWT parsing extensions. |
| **Testability & Speed** | **High Velocity**: Business rules can be thoroughly tested against high-speed in-memory SQLite sessions in sub-second test runs. | **Slow / Fragile**: In-memory SQLite cannot execute PostgreSQL RLS policies; tests require provisioning live Postgres Docker containers in CI. |
| **Observability** | **Explicit in Code**: Authorization constraints are directly visible in Python code and traceable via APM query logs. | **Opaque in SQL**: Authorization policies reside inside database migrations and system catalogs; debugging silent empty query returns is notoriously difficult. |
| **Defense-in-Depth** | **Gateway Protection**: Identity tokens are cryptographically verified and validated for revocation before any database thread is allocated. | Database must parse and decode JWT claims on every query, increasing CPU overhead inside the database cluster. |

---

## 4. Risks and Mitigations

### 4.1 Risk: Developer Omits `user_id` Filter in a Future Query
- **Threat**: A developer writes `select(Task).where(Task.id == task_id)` without checking `Task.user_id == current_user.id`, inadvertently exposing cross-tenant data.
- **Architectural Mitigations**:
  1. **Automated Cross-Tenant Pytest Suite**: Mandatory integration tests asserting that User B receives `404 Not Found` when requesting User A's resources across every endpoint (`SEC-ISO-01` through `SEC-ISO-04`).
  2. **Repository Abstraction Pattern**: Encapsulate queries inside scoped repository methods that require `user_id` as a non-optional parameter.
  3. **Automated CI/CD Lint Checks**: AST-based static analysis flagging unscoped queries against tenant-bound models.

### 4.2 Risk: Backend Credential Compromise
- **Threat**: If the backend database credentials (`DATABASE_URL`) are leaked, the attacker gains access to all tenant records because connections run with privileged rights.
- **Architectural Mitigations**:
  1. Database credentials are injected via runtime environment variables and secrets managers (never committed to version control).
  2. Network security: The PostgreSQL port (5432) is bound to an isolated private VPC subnet with zero ingress from the public internet. Only the application container IP can establish TCP connections.

## 3. Open Questions & Architectural Spikes (For Future Phases)

The following architectural questions have been identified during Phase 1 design and are scheduled for technical spikes prior to Phase 3 and Phase 4 implementation:

1. **Background Job Broker Selection (Phase 3 Spike)**:
   - *Question*: Should the background task queue use **Celery** with Redis, or an async-native alternative such as **ARQ** or **SAQ**?
   - *Trade-off*: Celery offers extensive operational monitoring tooling (Flower) but introduces heavy dependency baggage. ARQ runs natively on Python `asyncio` with minimal operational footprint.
2. **Rotating Refresh Token Architecture (Phase 3 Spike)**:
   - *Question*: Phase 1 specifies a 30-minute access token. Should Phase 3 introduce rotating refresh tokens stored in Redis or database-backed session tables?
   - *Trade-off*: Rotating refresh tokens improve SPA user experience while allowing instant session revocation.
3. **Model Context Protocol (MCP) Rate Limiting & Token Budgeting (Phase 4 Spike)**:
   - *Question*: How will autonomous AI agents safely invoke task planning tools without token budget exhaustion or cascading prompt injections?
   - *Trade-off*: MCP tool interfaces must enforce strict per-tenant execution rate limits and require explicit human-in-the-loop confirmation for destructive operations.
